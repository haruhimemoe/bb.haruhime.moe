# AGENTS.md

Rules for any agent (or human) working in this repo. Authoritative; `CLAUDE.md` only layers on top.

## 1. What this is

bb.haruhime.moe is an osu! BBCode editor with a live preview, plus templates: built-in ones (in the repo), people's own, and a public gallery. Anyone signs in with osu! to make, fork and report templates; admins clear reports. The binding spec is the vault note `05 - Notes/Projects/bb.haruhime.moe/Docs/Specs/2026-09-28-bb-design.md` (section 2). The editor (CodeMirror 6), the docs at `/docs`, the color, gradient and flag tools, previews, counts and template fills all run on `@haruhimemoe/bbcode`. So do the collab maker at `/collab`, the player list (the editor's Players tool and the collab maker's "Link players") and pool import from pools.haruhime.moe (the Pool tool); section 12 has their rules.

**Hard rule: we never host images.** No image, audio or video bytes pass through or are stored by our code. Templates hold URLs only; previews load them in the browser from their host. The CSP in `next.config.ts` opens `img-src` to `https:` and `media-src` to `https:` for that, and allows only YouTube's embed as a frame (`tests/unit/config/headers.test.ts`).

## 3. Code style

- TypeScript 7, `strict`, `noUncheckedIndexedAccess`. No `any`; validate external data with zod.
- Biome is the only linter and formatter (`bun run check`, `bun run check:fix`).
- No barrel files in `src/`. Import exact local paths. npm packages are imported from their published entry points.
- One component per file, PascalCase filename, Tailwind only. A component file exports only components and their prop types: copy goes in `src/constants/`, helpers in `src/utils/`.
- Take what the shared packages have instead of copying it: server plumbing from `@haruhimemoe/next-kit` (route helpers, rate limits, env, MongoDB and its indexes, the hub session reader, the account store and its menu), wired once in `src/lib/api.ts`, `rate-limit.ts`, `db.ts`, `db-indexes.ts`, `auth.ts`, `account.ts`, `template-routes.ts` and `src/env.ts`; UI pieces from `@haruhimemoe/ui`; the content filter from `@haruhimemoe/pool/content-filter`; osu! links from `@haruhimemoe/osu/shapes`; every osu! API call through `@haruhimemoe/osu`'s client (`getOsuClient`, never a hand-rolled token or fetch). A component ui lacks goes in `src/components/` and is noted as a ui candidate.
- Files stay under about 250 lines and components under about 200 (`tests/unit/tooling/file-size.test.ts`). No import cycles in `src/`.
- `utils/` is pure. Server-only modules `import "server-only"`. Client code never imports the `@haruhimemoe/osu` root (it holds the osu! secret; `tests/unit/tooling/client-imports.test.ts`).
- Rendered BBCode reaches the DOM only through `BbPreview`, which only renders `renderBbcode` from `src/lib/bbcode.ts`. Nothing else uses `dangerouslySetInnerHTML`.

## 4. File headers

Every `.ts`, `.tsx`, `.mjs`, and `.css` source file starts with:

```ts
/**
 * @file <repo-relative path>
 * @desc <what it is and why>
 * @author David @dvhsh (https://dvh.sh)
 * @created Ddd MMM D, YYYY
 * @modified Ddd MMM D, YYYY
 */
```

Dates match `date "+%a %b %-d, %Y"`. Update `@modified` on edits, never `@created`. Every export gets a doc comment right above it (one line is enough for a constant, type or schema); exported functions, components and route handlers get a JSDoc block with `@function`, `@param`, `@returns` (and `@throws` when they throw). `tests/unit/tooling/jsdoc.test.ts` checks every header and comment. Route files export only route handlers and Next's route options.

## 7. Legal copy and docs

- Docs, guides and legal pages are one registry, `CONTENT` in `src/constants/content.ts` (next-kit's `defineContent`): each entry is a slug, title, `navTitle` when the title is over 32 characters, description (140 to 160 characters for guides: it is the meta description and the lead), `lastUpdated`; a guide's search title is `GUIDE_SEO_TITLES`. URLs are `/docs/<slug>` (the API at `/docs/api`), `/guides/<slug>` and `/legal/<slug>`, each with a Markdown mirror at `<path>.md` (`contentRewrites()` in `next.config.ts` maps it to `<path>/md`, whose route answers an explicit `new Response("Not found.\n", { status: 404 })` for an unknown slug). A new page is three edits: the `.mdx` file, its registry entry and its line in `src/content/load.ts`; `tests/unit/content/registry.test.ts` fails until all three agree. The section routes under `src/app/{docs,guides,legal}/[slug]/` are the shared cookie cutter (packs, pools and haruhime.moe have the same); keep them that way. `bun run standards` (`next-kit check`) must pass. Bump `lastUpdated` with any wording change.
- bb's own docs parts stay bb's: the tag pages (`/docs/tags/<tag>`, `TagReference`, their `.md` at `src/app/docs-md/tags/` through their own rewrite) are `extra.docs` entries in the registry (group "Tags", badge `[tag]`), so the docs nav, `/docs` search, sitemap and llms.txt list them; `LiveExample`, `DocsFaq` and `<Example>` are bb's. In Markdown, `<Example source={"..."} />` becomes a fenced `bbcode` block through `exampleFences`, passed to next-kit's `readContentMarkdown` as a transform (`MARKDOWN_OPTIONS` in `src/utils/docs-markdown.ts`).
- `/brand` is `<BrandPage {...brandPageData("bb")} />`; its files in `public/brand/` come from `bunx haruhime-brand bb`.
- A new per-IP or per-account counter, or anything new we store, goes in `privacy.mdx`.
- A change people see updates the README's Features and, when it adds a page, `src/utils/llms-txt.ts` and the sitemap.
- SEO goes through `@haruhimemoe/next-kit/seo` with `SEO_SITE` (`src/constants/seo.ts`): the root layout is `siteMetadata`, the home page `homeMetadata`, every other page `pageMetadata` (canonical and og:url together; titles are "keyword · bb.haruhime.moe"; descriptions 140 to 160 characters) and missing ones `notFoundMetadata`. JSON-LD is built with `ld` and rendered with ui's `JsonLd`: docs in `src/utils/docs-seo.ts`, templates in `src/utils/template-seo.ts` (only listed templates: built in, or public and not hidden). The `/docs` FAQ (`src/constants/docs-faq.ts`) is visible and is the FAQPage; keep them one list. A page's `lastUpdated` (`src/constants/content.ts`) and `TAG_DOCS_UPDATED` feed the visible date, dateModified and the sitemap: bump them with any wording change. `/llms.txt` is next-kit's `contentLlmsTxt` (Docs with the tags, Guides, API, Legal) followed by bb's own sections; `/llms-full.txt` is `contentLlmsFull` with the tag pages and the FAQ after the registry's pages.
- No em dashes in any copy (`tests/unit/content/copy-rules.test.ts`). osu! wiki text is CC BY-NC and osu-web is AGPL: write from observed behavior, never copy.

## 8. Commits and PRs

- Conventional Commits (`feat:`, `fix:`, `chore:`, `docs:`, `test:`, `refactor:`).
- Titles past 60 characters end " · bb" instead of " · bb.haruhime.moe" (`SEO_SITE.shortTitleSuffix`, next-kit's `"auto"` default). Don't hand-shorten names.
- Link previews: listed templates (built in, or public and not hidden), every guide and every tag link their own card, `<page>/og.png`, drawn by `ogCard` from `@haruhimemoe/brand` (a dependency). `src/utils/og-card.ts` says what each card shows and versions its URL (`cardImage`) by that text. The guide and tag cards are prerendered with their pages (`force-static`); `/t/<id>/og.png` draws per request with a week-long CDN cache, so `next.config.ts` keeps brand and `@resvg/resvg-js` in `serverExternalPackages` (a native binary) and traces brand's fonts for it in `outputFileTracingIncludes`, keyed by a picomatch glob (`/t/*/og.png`; `[id]` would be a character class). Other pages keep the site image.
- 404s: a page that calls `notFound()` (a missing template) serves Next 16's empty `__next_error__` document with a 404, `noindex` and the root `not-found.tsx`'s metadata ("Page not found · bb.haruhime.moe"); a `generateMetadata` title never reaches it, and the browser renders the not-found UI. React's server renderer has no error boundaries, so the shell fails and Next falls back; a bare Next 16.3.6 app does the same, and unmatched or `dynamicParams = false` URLs render in full. Don't "fix" it with `loading.tsx` (a 200) or by dropping `notFound()`.
- Before pushing: `bun run check && bun run typecheck && bun run test && SKIP_ENV_VALIDATION=true bun run build`.
- When a change affects conventions, update this file in the same PR.

## 9. Templates

- The database is always `bb` (`DB_NAME` in `src/lib/db.ts`). Server env comes from `src/env.ts` only; `ADMIN_OSU_IDS` is read on every call. Never print a secret; never read `.env.local` in a tool call.
- `templates` (`src/models/Template.ts`, `src/schemas/template.ts`): `{ _id: "t-xxxxxxxx", ownerOsuId, ownerName, name (3..80), description (0..280), kind, body (1..60,000), fields[], visibility: private | unlisted | public, forkOf (null, a bare id from before history, or { docId, rev }), uses, reports, hidden, createdAt, updatedAt, version, head ({ id, seq }, the revision the row's content matches), historyPublic }`. Indexes: owner with updatedAt, visibility with updatedAt (Newest), visibility with uses (Most used), a text index on name and description (search), hidden. Ids are drawn by `newTemplateId` and drawn again on a clash.
- Fields (`src/schemas/template-field.ts`): `{ key, label, kind: text | multiline | number | date | url | user | users | country | color, required, default }`, keys unique, at most 40. Placeholders are `{{key}}`.
- Every typed text (name, description, body, field labels and defaults) goes through the content filter on writes (`src/schemas/text.ts`; refusal code `content_filter`). Reads use `templateReadSchema`, shape only, so a template a newer filter refuses still reads, can be renamed and deleted; a fork of it is refused until it passes.
- Who may do what is `src/utils/template-access.ts`: the owner everything; anyone sees unlisted and public templates that aren't hidden; admins also see hidden ones and never edit; can't see it 404, signed out on a write 401, sees it but may not 403. Built-in templates are 403 for edits, deletes and reports.
- Writes go through `src/lib/template-routes.ts`: session, `refuseCrossSite`, a strict JSON body of at most 512 KB, then a per-user limit keyed `osu:<osuId>` (next-kit's `userSubject`): `templateWrites` 30 a minute (create, edit, fork, delete), `templateReports` 10 an hour, `accountDelete` 3 an hour. "Use" (`POST /api/templates/<id>/use`) needs no session, is same-site only and counts 30 an hour per IP.
- Changes are versioned: `PATCH` carries `baseVersion` and, for a content change, `base` (the revision it started from). A content change with `base` is laid onto that revision and committed through `templateRevisions` (`src/lib/template-revisions.ts`): two tabs changing different lines merge (kind `merge`); the same lines conflict, 409 `merge_conflict` with the merged draft and its conflicts, so the form can show it with this tab's lines kept. A visibility-only PATCH needs no `base`: `baseVersion` alone guards it, a stale one is 409 `conflict` with the current template (`template` in the answer), which the form takes and reloads.
- Each account owns at most 100 templates: counted before the insert and again after it, which backs out when over.
- History: every template gets a revision store lazily (`ensureHistory`, `src/services/template-history.ts`), its root made from the content a pre-history template already had. Saves (and reverts) commit through `templateRevisions`, whose `check` reruns `templateContentSchema` on every write, so a merge, pull or revert can never land content today's filter refuses (400 with its code, nothing written). Owner only reads and reverts by default; `historyPublic` (owner-only toggle, `PUT /api/templates/<id>/history`) lets anyone who can see the template read its history too, except while it's private or hidden; admins read the history of any non-private template, hidden or not, but never revert or toggle. `POST /api/templates/<id>/history/<rev>/revert` restores a revision outright (no merge). Forks record `forkOf: { docId, rev }`, the upstream revision they last took in (`rev: null` for a legacy bare-id fork or a built-in's fork, filled in lazily on first read); `POST /api/templates/<id>/pull` 3-way merges the upstream's new head in, moving `forkOf.rev` forward on a clean merge, or handing back a 409 `pull_conflict` draft (the next PATCH's `pulled` field advances the base once the resolving save lands). Deleting a template or an account deletes its history (`templateRevisions.removeDoc`); a fork whose upstream is gone just reads "gone" in `upstreamStateOf`.
- Reports (`template_reports`: `{ templateId, reporterOsuId, reason, at }`, unique on template and reporter): each bumps `reports`; a public template at 3 is `hidden` (also when it becomes public with 3). Hidden stays set until an admin clears it (`DELETE /api/admin/templates/<id>/reports`: `reports` 0, `hidden` false, report rows kept so the same people can't report again). Admin routes answer 404 to everyone else first. `/admin` lists reported templates.
- Built-in templates are `content/templates/*.bb`: front matter (`name`, `kind`, `description`, `fields`, the small YAML subset `src/utils/front-matter.ts` reads) and the body, checked with the same content schema. Their id is `bb-<file name>`; their uses live in `builtin_template_uses`. They show on page 1 of the gallery marked "Built in", can be used and forked, never edited or reported. `tests/unit/content/builtin-templates.test.ts` checks every placeholder is declared and only osu! tags are used.
- The gallery, sitemap and llms.txt list public templates that aren't hidden; under `SKIP_ENV_VALIDATION` their database lists are empty. Counts run as the `count` command, not an aggregation.
- Sign-in belongs to the haruhime.moe hub. bb runs no better-auth: `src/lib/auth.ts` reads the hub's `better-auth.session_token` cookie (on `.haruhime.moe`) with next-kit's `createSessionReader` (signature checked with the shared `BETTER_AUTH_SECRET`, then `identity.session` and `identity.user` read, zero writes; banned users read as signed out through `requireSession`). bb's Atlas user has readWrite on `bb` and only read on `identity`: never write identity or build indexes there (`createMongo`'s `onConnect` only builds bb's). `/signin`, `requireUser` and `requireAdmin` redirect to the hub's `/api/signin/osu?next=<absolute bb URL>` (`hubSignInUrl` with `signInPath`, `HUB_URL`, default `https://www.haruhime.moe`), which goes straight to osu! and back to `next` on bb. Sign out is `POST /api/signout` (`src/lib/signout.ts`): cross-site refused, the server forwards only the session cookie to the hub's `/api/auth/sign-out` with `Origin: https://bb.haruhime.moe` (in the hub's trustedOrigins) and `redirect: "manual"`, then clears every better-auth cookie (`__Secure-` and bare) and the marker on `HUB_COOKIE_DOMAIN`; the browser reloads in place. The browser never POSTs to the hub (it sends no CORS headers). The only link to `https://www.haruhime.moe/account` is on bb's `/account` page, never the header menu or the palette. The `haruhime-signed-in` marker is the hub's; bb only reads it.
- User ids in bb data are identity user ids. The only field holding one is `api_keys.userId` (`USER_ID_REFERENCES` in `src/constants/db.ts`, for next-kit's `migrateIdentity`); templates, reports and revisions key people by osu! ID.
- "Delete my bb data" (`DELETE /api/account`) deletes the API key, the templates, their history, their reports, the reports it filed (each template it reported counts one fewer and is unhidden below 3, so deleting and saving again can't stack reports), and the API counters (`src/services/account.ts`). The haruhime account itself stays; it's deleted on the hub.

## 10. `@haruhimemoe/bbcode`

- `src/lib/bbcode.ts` is the one render seam: `renderBbcode` is the package's `render` (text nested too deep for 0.1.0's recursion comes back as escaped text instead of a `RangeError`, so one stored template can't break the gallery; the editor's lint gives no marks then), `countBbcode` its `count(...).length` (code points). `BbPreview` is its only HTML consumer.
- `src/utils/template-fill.ts` re-exports `fillTemplate` (returns `{ text, errors }`) and `templateFields` (returns `{ keys, undeclared, unused }`) from `@haruhimemoe/bbcode/template`; `fieldValue` and `missingRequired` are the form's own. A refused value stays `{{key}}` and `TemplateFill` names it.
- The toolbar (`src/constants/toolbar.ts`), autocomplete, the tag docs (`src/constants/tag-docs.ts`, one entry per TAGS name, tested) and `/docs/tags/<tag>` are all built from `TAGS`. A new tag in the package needs a `TAG_DOCS` entry.
- Full previews are laid out at `OSU_WIDTHS[target]` with `OSU_FONT_SIZES[target]` (`ScaledPreview`) and zoomed down with CSS `zoom` (never up; `fitZoom` in `src/utils/preview-scale.ts`, measured by `useFitZoom`'s ResizeObserver), so they wrap as osu! does; `zoom` keeps text crisp, layout height and pointer targets right. "Fit to pane / Actual size" (`ScaleToggle`) is `bb:preview-scale` in localStorage, shared by every preview on the page (`usePreviewScale`). The editor passes its target, templates `previewTargetFor(kind)`; `compact` cards (a server render) and `fluid` tool samples aren't scaled. The collab maker's drawing canvas isn't a preview and isn't zoomed.
- `package.json` pins `"@haruhimemoe/bbcode": "0.2.2"` from npm, like every other dependency (exact versions).

## 11. Editor

- `/` is static; `SourceEditor` loads through `next/dynamic` with `ssr: false`. Drafts are `bb:drafts` (`src/schemas/draft.ts`: `{ activeId, drafts: [{ id, name, text, updatedAt }] }`, at most 50); stage 1's `bb:draft` moves in once and is removed. A template's "Use" writes `bb:handoff`, which opens as a new draft. Another tab's save arrives as a `storage` event and is taken (`adoptStore`, keeping this tab's open draft), and a store taken unchanged isn't saved back. Every storage call goes through `src/utils/storage.ts`.
- Toolbar edits are data (`src/utils/text-edit.ts`: wrap or insert); `applyEdit` in `src/lib/codemirror/setup.ts` applies one to the selection. A wrap that's already there unwraps.
- Tools open one at a time under the toolbar: Color, Gradient, Flag (small PNG flags by default; SVG ones fill the width they're shown in), Players and Pool. Color, Gradient and Flag close after inserting; Players and Pool stay open so what they report stays in view.
- Component tests reach CodeMirror through `tests/helpers/editor.ts`; `tests/setup/components.ts` stubs the Range measurements jsdom lacks. user-event reads `[` as a key, so type `[[` for a bracket.

## 12. Collab maker, player list, pool import

- `/collab` is static and runs in the browser. Its state is one reducer (`src/utils/collab.ts`: `{ image, regions: [{ id, x, y, w, h, href, title }], selected }`), positions in percent of the image, rounded to 2 decimals, at least 1% a side and inside the image (`src/utils/region-geometry.ts`). Output is `@haruhimemoe/bbcode/imagemap`'s `serializeImagemap` after `validateImagemap` (a problem shows on its field and holds the output back); import is `parseImagemap`. The image is an `<img>` from its own host (http or https typed; an http one gets a note that https pages, osu! included, may refuse it). Pointer events (mouse, pen, touch) all go to one overlay with `touch-action: none` (`useRegionPointer`); regions and handles are found by `data-region-id` and `data-handle`. Arrow keys move the focused region by 0.5% (Shift 5%), Alt with arrows resizes, Delete removes. The image URL and regions are kept in localStorage as `bb:collab` (`{ image, regions }`, `src/utils/collab-storage.ts`, read back through a schema, regions fitted again with fresh ids), restored once after the first render by `useCollabStorage`, saved on every change, and removed by Clear or an empty maker.
- Player lookups: `POST /api/osu/users` (no session, `refuseCrossSite`, `userLookups` 20 a minute per IP, body `{ names }` of 1 to 64) answers `{ users, notFound, unchecked }` with users in the order asked, each once. `src/utils/player-names.ts` reads ids, names and osu.ppy.sh profile links; a line that's none of them is notFound. `src/services/osu-users.ts` asks osu! through `@haruhimemoe/osu`'s client (`getOsuClient` in `src/lib/osu.ts`: `getUsers` for ids, 50 a call; `getUser` for names, one a call as `/users/@name`; its errors are `OsuApiError`, which the route turns into a 503) and keeps answers in `osu_users` (`{ _id: "id:<n>" | "name:<lower>", user | null, expiresAt }`, 24 h found, 1 h not found, TTL on `expiresAt`). Unknown names are always shown (`LookupReport`), never dropped.
- Every osu! call, from lookups or pool import, first takes one from `osuBudget` (`src/lib/osu.ts`, next-kit's `createBudget`: 50 a minute across instances, 20 a minute per IP, in `rate_limits`). What the budget leaves unasked comes back `unchecked` (lookups) or with `stars: null` and `complete: false` (pools).
- Pool import: `GET /api/pools/<id>` (no session, `poolImports` 20 a minute per IP) reads a built pool (`b-` plus 8) from pools' public `GET /api/pools/<id>` at `POOLS_URL` (`getPoolsUrl`, default `https://pools.haruhime.moe`) without cookies; pools answers 404 for private, hidden and missing pools, and so do we. Past pools have no JSON API on pools, so their ids (and links) are refused by name (`src/utils/pool-ref.ts`, 400 `past_pool`). pools' built pool answer carries slots but no map details or ratings, so `src/services/pool-import.ts` asks osu! (`@haruhimemoe/osu`'s `getBeatmaps` and `getStarRating`) and keeps each map in `osu_beatmaps` (`{ _id, artist, title, version, creator, stars: { "": nm, "HDHR": ... }, expiresAt }`, a week). A bucket's stars are for `slotModsFor`'s forced set; NM, FM, TB and free custom buckets use no-mod stars. A complete answer is `s-maxage=300`; anything else is `no-store`. `src/utils/pool-import.ts` writes the BBCode (names through `escapeBBCode`).
